# Portfolio 3 - Transactions and concurrency (7 marks)
The runner uses independent connections for locking/isolation experiments. Scenarios: exact debit/credit commit; forced exception after posting with full rollback; reversal and duplicate-key retry; two competing withdrawals whose combined value exceeds funds (one commits and one rejects); held wallet lock with observed lock wait and release; READ COMMITTED versus REPEATABLE READ visibility; SERIALIZABLE read-modify-write conflict in a disposable probe table. Check raw logs for commit/rollback outcomes and SQLSTATEs.

Atomicity: function changes ledger/transfer/outbox in one transaction. Consistency: deferred posting constraints plus checks and FKs. Isolation: ordered row locks serialize shared wallets under READ COMMITTED; REPEATABLE READ/SERIALIZABLE may require full-transaction retry after 40001. Durability: committed state survives normal PostgreSQL restart in the persistent volume when the restart check runs; this does not prove power-loss, disk-loss or backup recovery. Deadlock avoidance applies to the function's ordered wallet locks, not every possible future application lock sequence. Retry keys prevent duplicates; mismatched reuse is rejected. Logs are not a personal reflection.
