# Relational schema and invariants
Customers(customer_id PK, full_name, email UNIQUE, created_at). Wallets(wallet_id PK, customer_id FK nullable for clearing, kind, currency); UNIQUE(customer_id,currency); only NGN is supported. Customers have zero or one NGN wallet, clearing has no customer. Transfers(transfer_id PK, request_key UNIQUE, sender_id FK, receiver_id FK, amount, status, reversal_of UNIQUE self FK, created_at). Ledger_entries(entry_id PK, transfer_id FK, wallet_id FK, amount); UNIQUE(transfer_id,wallet_id). Outbox_events(event_id PK, transfer_id UNIQUE FK, event_type, payload, created_at, delivered_at).

Each posted transfer has exactly two ledger entries: sender -amount, receiver +amount; total ledger is zero. Customer balance must stay nonnegative; clearing can be negative. NUMERIC avoids binary float rounding and the function rejects fractional kobo. The posted-only status describes committed movements; a failed request has no financial transfer. Failed-attempt auditing is a proposed separate operational log, since an audit row in an aborted transaction also rolls back. A reversal is another posted movement, once per original. It may fail if the recipient has already spent the money; there is no forced overdraft or fictional recovery.

The schema's deferred constraint triggers reject incomplete postings at commit. Ordered wallet locks and restricted write privileges protect concurrent normal application use. Direct writes by an owner are outside this trust boundary: a privileged owner could disable triggers or violate application locking. Ledger and transfer updates/deletes are rejected, but a database owner can still TRUNCATE/alter tables. Production requires stronger role separation, administrative audit, encrypted transport, backup and restore testing.
